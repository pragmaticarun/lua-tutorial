# Contributing / authoring conventions

The one rule: **no untested code in the docs.** Every Lua snippet shown on the
site is a real file under `examples/`, included into Markdown with
`pymdownx.snippets`, and every output block is an `.expected` file that
`tests/run_all.sh` compares against.

## Layout

```
examples/NN-slug/name.lua             the snippet (included verbatim in the docs)
examples/NN-slug/name.expected        expected stdout (shown in the docs)
examples/NN-slug/name.<id>.expected   optional per-interpreter override
                                      (<id> = 5.5 | 5.4 | jit)
examples/NN-slug/name.input           optional stdin, declared in the header
examples/NN-slug/name.c / name.cpp    C / C++ snippet with a "// build:" header
examples/NN-slug/build/               compiler output (git-ignored)
examples/NN-slug/Cargo.toml           a Rust crate; each src/bin/name.rs is an
                                      example with src/bin/name.expected beside it
includes/bench/*.md                   measured benchmark tables (tests/bench.sh)
includes/badges/NN-slug.md            "Tested with" badge, generated by the runner
tests/results/versions.txt            interpreter versions from the last run
```

## Header comments (first 5 lines of a .lua file)

```lua
-- targets: 5.5, 5.4      -- only run on these interpreters (default: all three)
-- stdin: name.input      -- feed this file on stdin
-- module                 -- a library file used via require by other examples;
                          -- the runner does not execute it directly
```

Use `targets` only for code that cannot run elsewhere (new syntax or library
functions), and say so in the lesson. Use a per-interpreter `.expected`
override only for **intentional, documented** output differences, and show
them in the page with content tabs.

## Workflow

```bash
tests/bless.sh 07-                    # create missing .expected files (first target)
tests/bless_overrides.sh examples/07-patterns/foo.lua   # write overrides where output differs
# READ the generated files: blessing is not testing
tests/run_all.sh                      # full run; regenerates includes/badges
.venv/bin/mkdocs build --strict
```

Examples run with the example's directory as the working directory and the
file name as the chunk name, so error messages look like `foo.lua:3: ...`
on every machine. Avoid output that depends on addresses (`table: 0x...`),
`pairs` order, time, or platform-specific float text such as `-nan`.

## C, C++ and Rust examples

The header comments work the same way with `//`. A C or C++ file needs a
`build:` line:

```c
// build: exe        compile against each target interpreter's headers and static
//                   library (build/<id>/name), run it, compare stdout
// build: module     compile a Lua C module build/<id>/name.so; Lua examples in the
//                   same directory run with LUA_CPATH="./build/<id>/?.so;;"
// build: shared     plain shared library build/libname.so (for the LuaJIT FFI)
// targets: 5.5, 5.4 as for Lua
```

Files without a `build:` line (headers, helpers) are not compiled on their own.
Rust crates are built once per target with `--no-default-features --features
lua55|lua54|luajit`, linked statically against the same interpreter builds
(`LUA_LIB`, `LUA_LIB_NAME`, `LUA_LINK=static`), and every binary in `src/bin/` is
an example. `tests/bless.sh` and `tests/bless_overrides.sh` handle all languages.
Warnings are errors (`-Wall -Wextra -Werror`).

## Host examples (Part 4)

Part 4 examples run inside real applications, installed (pinned) by
`scripts/install-hosts.sh`:

```lua
-- host: nvim        run with `nvim --headless --clean -l name.lua`, compare stdout
-- host: redis       (any other host) not run on its own: a *.test.sh driver uses it
```

```bash
# host: openresty, redis    first line(s) of name.test.sh: the hosts it needs
. ./openresty.sh            # drivers are plain bash, run from their directory;
or_start || exit 1          # stdout is compared with name.expected
```

- Drivers must be deterministic: no timestamps, addresses, timings or hash-order
  output in stdout (sort it, or print a yes/no check instead).
- The runner starts one Redis server on `$REDIS_PORT` for the whole run and flushes
  it (data, scripts, functions) before every test that lists `redis`.
- A missing host makes its tests **skip** (and the badge says so); never paste
  output that was not produced by the host.
- Under `nvim -l`, `print()` goes to stderr: write test output with `io.write`.
